# RootLens C2PA 信頼モデルとセキュリティ限界

## 概要

RootLensは「アプリベースC2PA」として、ハードウェアメーカー（Google Pixel, Sony Alpha, Leica）とは異なる信頼レベルを提供する。本文書はその信頼モデルの位置付け、アーキテクチャ上のトレードオフ、既知のセキュリティ限界を明示する。

## なぜ証明書チェーン（PKI）を使うのか

### C2PA仕様がPKIを要求している

C2PAの署名はCOSE Sign1形式で、x5chain（証明書チェーン）が必須フィールドである。

```
COSE_Sign1 = [
  protected: { alg: ES256 },
  unprotected: { x5chain: [DeviceCert, ICA, RootCA] },
  payload: C2PA Manifest,
  signature: ECDSA署名
]
```

PKIなしではC2PA準拠にならず、Adobe Content Credentials、Google Pixel、Sony Alpha等の汎用C2PAビューアで検証できない。**エコシステム互換性のためにPKIは必須。**

### PKIを使わない代替案とその問題

| 方式 | 仕組み | 問題 |
|------|--------|------|
| サーバーサイド署名 | 撮影→サーバーにアップロード→サーバーが署名 | サーバーに秘密鍵が集中。サーバー侵害=全偽造可能。オフライン署名不可 |
| 自己署名鍵 | デバイスが鍵生成し自己署名 | 「誰が発行した鍵か」が不明。攻撃者が自由に鍵を作れる |
| オンチェーン鍵登録 | Attestation通過後、公開鍵をブロックチェーンに登録 | C2PA非準拠。検証にオンチェーン照会が必要 |

C2PA仕様がPKIを要求していなければ、「Attestation通過→公開鍵をオンチェーン登録」で同等のセキュリティは達成可能だった。PKIの運用コスト（KMS管理、CRL運用、ICAローテーション）はC2PAエコシステムに参加するための必要経費である。

### 既存サービスとの比較

**Truepic**（アプリベースC2PA、最も近い先行事例）: PKI/証明書チェーンを使用。ただしサーバーサイド署名。撮影→即アップロード→サーバーが署名。デバイスにTEE鍵なし。

**Numbers Protocol**: ブロックチェーンベースの来歴管理。C2PA非準拠。PKIなし。

**ProofMode (Guardian Project)**: PGP鍵で署名。C2PA非準拠。

C2PA準拠のアプリベース実装でPKIを使わないものは存在しない。

## C2PA Assurance Level

| レベル | 代表例 | 署名の意味 |
|--------|--------|-----------|
| Level 2 | Google Pixel (Titan M2), Sony Alpha, Leica | 「このカメラハードウェアで撮影された」 |
| Level 1 | **RootLens** | 「正規デバイス上のRootLensアプリがTEE鍵で署名した」 |

### RootLensが証明できること

- C2PA署名がデバイスTEE（Secure Enclave / StrongBox）内の秘密鍵で行われたこと
- その鍵に対応するDevice CertificateがRootLens PKIチェーンで発行されたこと
- プロビジョニング時にPlatform Attestation（Android Key Attestation / iOS App Attest）を通過したこと

### RootLensが証明できないこと

- コンテンツがカメラで実際に撮影されたこと（アプリ層での署名のため、カメラパイプラインとの直結は保証されない）
- 署名時点でデバイスが改竄されていないこと（Attestationはプロビジョニング時のみ）

## アーキテクチャ上のトレードオフ: サーバー集中 vs デバイス分散

RootLensはデバイス側にTEE鍵を持たせ、署名をデバイス内で完結させる設計を採用している。この設計にはサーバーサイド署名と比較して明確なトレードオフがある。

### デバイス分散の利点: 爆発半径の封じ込め

```
【サーバーサイド署名（Truepic型）】
  鍵: サーバーに1個
  サーバー侵害 → 全ユーザー・全デバイスを偽装可能
                → 正規署名と偽造の暗号的区別が不可能
                → 復旧にはRoot CA再生成、全デバイス再プロビジョニング
                → サービス全体の信頼が崩壊

【デバイスサイド署名（RootLens型）】
  鍵: 各デバイスのTEE内にN個
  1台の侵害 → そのdevice_idでのみ偽造可能
             → 他デバイスは暗号的に独立、完全に無傷
             → CRLで1枚のDevice Certificateを失効するだけで復旧
             → システム全体の信頼は維持
```

| | サーバー侵害 | デバイス1台侵害 |
|--|-------------|---------------|
| 偽造可能な範囲 | 全ユーザー・全デバイスを偽装 | その1台のdevice_idだけ |
| 検出 | 困難（正規署名と暗号的に区別不可能） | 可能（異常な署名頻度、地理的矛盾等） |
| 復旧 | Root CA再生成、全端末再発行 | CRLで1枚失効 |
| 過去コンテンツ | 全て疑わしくなる | 他デバイスの過去コンテンツは安全 |

### デバイス分散の代償: 攻撃面の拡大

一方で、デバイスの数だけ攻撃面は広がる。

- サーバーサイド: 攻撃対象は1箇所（サーバー）。専門チームによる防御が可能
- デバイスサイド: 攻撃対象はN百万台の消費者デバイス。個々の端末の物理セキュリティは制御不能

**ユーザー数が増えるほど「どこかの1台が破られる確率」は1に近づく。**

1台が破られた場合、その鍵で偽コンテンツを量産できる。C2PA署名はデバイス内でローカルに完結するため、署名時にサーバー側で止める手段がない。CRLは事後対応でしかなく、検出が遅れれば被害は拡大する。

### このトレードオフの判断

セキュリティ工学における古典的な「集中型 vs 分散型」の信頼設計:

- **集中型**: 侵害確率は低いが、発生時の被害は壊滅的。復旧コストが極めて高い
- **分散型**: 長期的にはどこかの1台の侵害はほぼ確実。だが被害は局所的で封じ込め可能

RootLensはデバイス分散を選択している。理由:

1. サーバー侵害によるサービス全体の信頼崩壊は、個別デバイス侵害より遥かに深刻
2. デバイス侵害はCRL+短寿命証明書で被害を限定できる
3. TEE（Secure Enclave / StrongBox）の実際の侵害コストは非常に高い
4. 異常検知（署名頻度監視、Title Protocol登録時のパターン分析）で早期発見が可能

## 攻撃シナリオ分析

### 1. 未root端末での偽装

**攻撃**: 正規端末でRootLensアプリを使い、他のアプリで作成した画像を「撮影した」と偽って署名させる。

**防御**: RootLensアプリはカメラAPIから直接取得した画像のみ署名する設計。アプリが改竄されていない限り、この攻撃は成立しない。正規端末ではアプリの改竄にrootが必要。

**リスク**: **極めて低い**

### 2. 事前root端末でのプロビジョニング

**攻撃**: root化済み端末でAttestation検証を突破し、Device Certificateを取得する。

**防御**:
- Android Key Attestation: ハードウェアレベルで署名されるため、rootだけでは偽装不可能。bootloader unlocked状態がAttestationに含まれ、サーバーで拒否可能
- Play Integrity API: `MEETS_DEVICE_INTEGRITY` / `MEETS_STRONG_INTEGRITY` でroot端末を検出
- iOS App Attest: Secure Enclaveベースの証明。jailbreakでの偽装は極めて困難

**リスク**: **低い**（Attestation実装後。未実装の現状ではP0ブロッカー）

### 3. 正規プロビジョニング → 事後root化 → コンテンツ注入（主要リスク）

**攻撃フロー**:
```
1. 正規デバイスでAttestation通過、Device Certificate取得（90日有効）
2. デバイスをroot化
3. アプリを改竄（Frida/Xposedでフック、またはAPKパッチ）
4. 偽コンテンツをTEEに署名させる
5. 有効なDevice Certificateがあるため、検証を通過する
```

**なぜ署名時にサーバー側チェックを入れられないか:**

C2PA署名はカメラ撮影時にデバイス内でローカルに完結する。オフラインでも動作する必要があり、署名のたびにサーバーとの往復はUX的にもオフライン対応的にも不可能。また、署名済みC2PAコンテンツは自己完結しているため、登録時のチェックも防御にならない（署名済みファイルはどこからでも登録可能）。

**防御**:

| 対策 | 効果 | 限界 |
|------|------|------|
| Bootloader unlock→Factory Reset | 大半のroot手段で鍵+証明書が消失 | exploitベースのrootは対象外 |
| 短寿命証明書（90日） | 攻撃窓口を限定 | 期間内は有効 |
| CRL（証明書失効） | 不正検出後に即失効 | 事後対応であり予防ではない |
| renewでの再Attestation | 更新時にデバイス健全性を再確認 | 更新前の期間は防げない |
| 異常検知（署名頻度監視） | Title Protocol登録時にパターン分析が可能 | ローカル署名自体は止められない |

**このシナリオは原理的に完全には防げない。アプリベースC2PAの本質的な限界。**

### 4. TEE鍵の抽出

**攻撃**: TEEから秘密鍵を抽出し、任意の環境で署名する。

**防御**:

| TEE種別 | root耐性 | 対象 |
|---------|---------|------|
| StrongBox (Titan M2等) | ハードウェア隔離。既知の抽出手法なし | Pixel 6+, Galaxy S21+ |
| TEE (ARM TrustZone) | ソフトウェア隔離。理論上脆弱性の可能性あり | 多くのAndroid端末 |
| iOS Secure Enclave | 専用チップ。既知の抽出手法なし | iPhone/iPad全モデル |

**リスク**: **極めて低い**（StrongBox/Secure Enclave使用時）

## 攻撃者プロファイルと実行可能性

シナリオ3（正規プロビジョニング→事後root化→コンテンツ注入）の実行には、以下が必要:

1. **root化（鍵と証明書を保持したまま）**: 一般的なBootloader unlock方式ではFactory Resetにより鍵+証明書が消失し、再プロビジョニング時にAttestationで弾かれる。exploitベースのrootが必要だが、未パッチの脆弱性は端末固有で月次パッチで塞がれる
2. **アプリ改竄**: Frida/XposedでRootLensのC2PA署名フローをフック。Rustネイティブ層+JNI/FFI層の逆解析が必要
3. **TEE署名の誘導**: 改竄したアプリ経由で偽コンテンツをTEEに署名させる

| 攻撃者レベル | 実行可能性 | 必要条件 |
|-------------|-----------|---------|
| 一般ユーザー | **不可能** | bootloader unlock→reset→attestation失敗で詰む |
| 技術に詳しいユーザー | **不可能** | 未公開exploitを自力で発見できない |
| セキュリティ研究者 | **可能だが高コスト** | 端末固有exploit + アプリ逆解析（数日〜数週間） |
| 国家レベルの攻撃者 | **可能** | RootLens偽装の動機があるかは別問題 |

攻撃をツール化して配布するリスクはあるが、端末固有exploit依存のため汎用化が困難。月次セキュリティパッチで無効化される。C2PA普及初期のためツール作成の動機も低い。

## ハードウェアC2PAとの根本的な違い

```
【Google Pixel C2PA】
  カメラセンサー → Titan M2 (ハードウェア署名) → C2PA出力
  アプリ層を一切経由しない → root化でもコンテンツ注入不可能

【RootLens C2PA】
  カメラAPI → アプリ層 → TEE署名 → C2PA出力
           ↑
    root+改竄でここに介入可能（署名前にデータを差し替え）
```

この差はアプリベースである限り埋められない。

## 結論: RootLensの信頼モデル

RootLensのC2PA署名は、署名の偽造を不可能にすることではなく、**偽造コストを十分に高くすること**を目標としている。

```
偽造コスト
  ↑
  │  Pixel C2PA: Titan M2ハードウェア攻撃（現時点で実質不可能）
  │
  │  RootLens: TEE exploit + リバースエンジニアリング + root化 + 90日以内
  │            （セキュリティ研究者レベルの技術が必要）
  │
  │  署名なし: ゼロ（誰でもPhotoshopで加工可能）
  ↓
```

デバイス分散モデルは「どこかの1台がいつか破られる」確率を受け入れる代わりに、「1箇所の侵害で全崩壊」するリスクを排除する。侵害が発生した場合もCRL+短寿命証明書で被害を局所的に封じ込められる。

> RootLensは、プロビジョニング時のPlatform Attestationにより正規デバイスであることを検証し、
> TEE保護された鍵で署名することで、一般ユーザーや技術者による偽造を実質不可能にする。
> 高度な攻撃者による事後root化+コンテンツ注入の理論的リスクは存在するが、
> 実行コストが高く、短寿命証明書（90日）+CRLにより被害は限定される。
> サーバーサイド署名と比較して、攻撃面はデバイス数だけ広がるが、
> 個々の侵害の爆発半径は1台のdevice_idに封じ込められ、
> システム全体の信頼は維持される。

Public Pageでは C2PA Assurance Level を表示し、ハードウェアC2PA（Level 2）とアプリC2PA（Level 1）を明確に区別する。ユーザーが信頼度を判断できるようにする。
